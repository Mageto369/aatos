WORK PACKAGE 2: REFRESH TOKEN ROTATION

Objective:

Replace stateless JWT refresh tokens with opaque, database-backed, rotating tokens.

Required design:

Generate a cryptographically secure opaque token.
Store only a hash of the token.
Associate the token with:

User ID
Session ID
Token family
Created time
Expiration time
Last-used time
Revoked time
Replacement token ID
IP address where appropriate
User agent where appropriate

Required behavior:

Each successful refresh invalidates the current token.
Each successful refresh issues a new access token and a new refresh token.
Reusing an already-rotated token revokes the entire token family.
Logout revokes the active session.
Password reset revokes all user sessions.
User suspension revokes all sessions.
Administrator session revocation works.
Expired tokens fail.
Malformed tokens fail.
Raw refresh tokens never appear in logs or database records.

Add migration for refresh-token or session records.

Add cleanup for expired and revoked tokens.

Use secure cookie settings where the frontend architecture supports cookies:

HttpOnly
Secure in staging and production
SameSite based on deployment topology
Narrow path
Explicit expiration

Do not store refresh tokens in localStorage.

Exit criteria:

Rotation test passes.
Reuse-detection test passes.
Logout revocation test passes.
Password-reset revocation test passes.
Suspended-user test passes.
Concurrent-refresh behavior is defined and tested.
Real commit created.
